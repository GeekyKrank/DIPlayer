# Сервер каталога DIPlayer

Сервер написан на ASP.NET Core 10 и развёрнут на существующей Oracle Always Free VM donbot (Ubuntu 24.04, x86_64, 1 ГБ RAM). Проверены официальный API и публичный HTTPS: https://158-180-35-133.sslip.io/diplayer/ . Этот адрес задан по умолчанию в новых установках клиента. Бот и мини-приложение на той же VM сохранены и работают.

## Что делает

Фиксированные маршруты: GET /health, /search?q=, /resolve?url=, /playlists/{id}/tracks, /tracks?ids=, /tracks/{id}, /tracks/{id}/stream. Поиск и плейлисты — страницы по 25. Stream возвращает подписанный CDN-адрес без OAuth-токена; аудио скачивает клиент напрямую.

Секрет и refresh token не возвращаются клиенту. Метаданные и музыка на сервере не кешируются. Сохранён только файл действующего токена для повторного использования после рестарта. Обновление токена сериализовано; сервис запускается в одном экземпляре. Запуск нескольких экземпляров с общим token.json не поддерживается.

Максимум четыре выполняющихся запроса, общий бюджет два запроса в секунду с burst 6, 30 запросов в минуту на IP и 3000 запросов за 24-часовое окно сервиса. Счётчики в памяти сбрасываются при рестарте; это ограничитель нагрузки, не облачный платёжный лимит. Nginx перезаписывает X-Forwarded-For реальным адресом клиента; сервис доверяет только loopback proxy. Посторонний X-Forwarded-For не должен менять identity лимитера. Открытый API всё равно может быть исчерпан посторонним клиентом; неограниченная нагрузка не поддерживается.

После проверочных запросов systemd показывал MemoryCurrent/Peak около 89 МиБ и CPUUsage 2,19 секунды с момента запуска. Это cgroup-учёт короткой серверной проверки, а не часовой нагрузочный бенчмарк. Ограничения сервиса: MemoryMax=160M, CPUQuota=25%. Новых VM, дисков и балансировщиков не создавалось. В облачной консоли текущая VM помечена Always Free; это не гарантия будущих тарифов или расходов при изменении ресурсов.

## Развёртывание на существующей Linux VM

Сначала убедиться в архитектуре VM и в том, что использование укладывается в условия Free Tier конкретного tenancy. Эти условия и фактические расходы здесь не проверены. Не создавать платные VM, диски и балансировщики автоматически.

1. Собрать `pwsh -File tools/Build.ps1 -WithServer -ServerRid linux-arm64` для Ampere либо `linux-x64` для AMD.
2. Разместить файлы опубликованного сервера в `/opt/diplayer`, сделать `DIPlayer.Server` исполняемым.
3. Создать отдельного системного пользователя `diplayer` без интерактивного входа. Бинарные файлы должны принадлежать root и не быть доступны сервису на запись.
4. Создать `/etc/diplayer/secrets.env` по примеру `deploy/secrets.env.example`. Внести ключи непосредственно на сервере; файл root:diplayer с правами 0640, каталог 0750. Не вставлять секреты в shell history, Git или чат.
5. Установить unit из `deploy/diplayer.service`. Он слушает только 127.0.0.1:5080, использует StateDirectory, UMask=0077, MemoryMax=160M и CPUQuota=25%. Лимиты — конфигурация, не подтверждённый серверный бенчмарк.
6. Настроить Caddy с действительным доменом и HTTPS. Образец в deploy. Открывать наружу только HTTPS сервиса, а не 5080. Изменения сетевого доступа выполнять отдельно после проверки конкретной VM.
7. Проверить /health, затем поиск, плейлист и выдачу потока; запустить `tools/Test-Server.ps1 -BaseUrl https://реальный-домен` и проверить квоты. Перезапустить сервис и убедиться, что токен повторно используется.
8. В Windows-приложении открыть ⚙ и указать HTTPS-адрес сервера.

Сервис не является аудиопрокси, не хранит музыку и не обходит региональные ограничения. Доступность API с адреса Oracle и доступность CDN у слушателя могут отличаться. При таком несовпадении трек должен завершаться ошибкой, а не скрыто перенаправляться через сервер.

## Перед публичным выпуском

Нужны реальное развёртывание, проверка тарифов/квот, настройка reverse proxy, испытание Linux-сборки, разрешённость сценария по условиям SoundCloud и решение о защите общего бюджета. Локальный успешный тест не означает, что сервер уже готов обслуживать произвольное число пользователей GitHub.
